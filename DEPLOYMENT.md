# Deployment Guide

## Current hosting topology

This project runs in the managed WebDev environment with a Vite/React storefront, Node/Express/tRPC server, managed MySQL/TiDB database, Manus OAuth, managed object storage, and Shopify Storefront API integration. HTTPS and the preview edge are supplied by the platform. Production behavior is request-based/serverless; do not assume a persistent worker or in-memory queue survives requests.

## Local / preview checks

From the project directory:

```bash
pnpm check
pnpm test
pnpm build
pnpm shopify:probe
```

The Shopify probe needs a configured store domain and Storefront API access token and will fail/skip when those are absent, as described in the integration guide. Cart testing needs at least one published product with an available variant.

## Environment variables

Set secrets through project secrets/settings, never in frontend code, source control, or terminal output. Values beginning with `VITE_` are public; never place secrets there.

- Managed platform: `DATABASE_URL`, `JWT_SECRET`, Manus OAuth values, built-in storage/API environment supplied by the runtime.
- Shopify server: `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_STOREFRONT_API_ACCESS_TOKEN` (server-side only).
- Protected product-image uploader: `SHOPIFY_ADMIN_ACCESS_TOKEN` (server-side only). Create/install a Shopify custom app with `write_files` and `write_products` scopes; never use a `VITE_` variable for this token.
- Admin role bootstrap on Render: configure `OWNER_OPEN_ID` for the intended store owner, or promote the approved account's database role to `admin` through the trusted database/admin process. Never accept role changes from the browser.
- Optional future M-Pesa: `MPESA_CONSUMER_KEY`, `MPESA_CONSUMER_SECRET`, `MPESA_PASSKEY`, `MPESA_SHORTCODE`, `MPESA_CALLBACK_URL`, and a Daraja environment/sandbox selector. Do not add live values until callback URL ownership and merchant credentials are confirmed.
- Public metadata: `NEXT_PUBLIC_APP_URL` in the original brief is framework-specific and not used by this Vite scaffold; use the managed public site URL or a documented Vite public variable where required.

## Render Blueprint

The repository root includes `render.yaml` for a Node web service. It pins Node.js 22.22.0 (the version family used to validate this project), builds with `pnpm install --frozen-lockfile && pnpm build`, and starts with `pnpm start`. The service is set to Render's Free plan for preview use and Frankfurt for the Kenya-first storefront. Render does not allow changing a service's region after creation, so change `region` in the Blueprint before creating the service if another region is preferred.

The Blueprint intentionally contains no credentials. Render prompts for values marked `sync: false`; enter them in Render's environment settings, never in Git. `JWT_SECRET` is generated by Render. Required external values include a Render-reachable **MySQL/TiDB** `DATABASE_URL` (this app uses Drizzle's MySQL driver, not Render Postgres), Manus OAuth values (`VITE_APP_ID`, `OAUTH_SERVER_URL`, `VITE_OAUTH_PORTAL_URL`), Manus Forge storage/API values (`BUILT_IN_FORGE_API_URL`, `BUILT_IN_FORGE_API_KEY`, `VITE_FRONTEND_FORGE_API_URL`, `VITE_FRONTEND_FORGE_API_KEY`), and Shopify (`SHOPIFY_STORE_DOMAIN`, `SHOPIFY_STOREFRONT_API_ACCESS_TOKEN`). To enable `/admin/product-images`, also supply `SHOPIFY_ADMIN_ACCESS_TOKEN` from an installed custom app with `write_files` and `write_products` scopes, and set the intended user's `OWNER_OPEN_ID` or grant the `admin` role in the database. The `VITE_` values are bundled into browser code; only provide values intended for client-side use.

Before login can work, register the new Render origin's callback URL with the OAuth application: `https://<your-render-service>.onrender.com/api/oauth/callback`. Apply the existing Drizzle/MySQL schema to the external database before relying on account features. Confirm the Manus Forge credentials are valid for requests from an external host; Render does not inherit the managed WebDev environment or its secrets. If they are not valid externally, move the required media/API functionality to a host-supported service.

**Free-plan caveat:** Render says Free web services are for testing/hobby use, not production. They spin down after 15 minutes without inbound traffic and can take about a minute to start again; free filesystems are ephemeral. This store is still a preview and does not accept real payments. Sources: [Render Blueprint specification](https://render.com/docs/blueprint-spec), [environment variables](https://render.com/docs/configure-environment-variables), [Node.js version selection](https://render.com/docs/node-version), and [Free instance limitations](https://render.com/docs/free).

## Go-live checklist

1. Claim/verify the newly provisioned Shopify development store through project settings; replace the preview product with the owner's approved, accurately described catalog and image assets.
2. Confirm products are active, priced in the intended currency, stocked, and published to the Manus storefront channel; run `pnpm shopify:probe` and test add/update/remove cart operations.
3. Configure Shopify checkout, shipping zones, tax behavior, order notifications, returns policy, and a Kenya-supported payment method. M-Pesa availability must be confirmed in the merchant's Shopify/provider settings; do not advertise it until a sandbox/live payment is verified.
4. Configure domain, contact details, privacy/terms/returns/shipping pages, email/SMS providers, analytics consent, backups, monitoring and alert ownership.
5. Run `pnpm check`, all tests, responsive/accessibility checks, payment failure tests, order reconciliation and a low-value end-to-end sandbox purchase.
6. Set production secrets in managed project settings, publish a checkpoint, deploy through the platform's publish flow, then verify HTTPS, health, catalog, checkout and callback behavior in production.
7. Keep rollback instructions and store/database backup ownership documented.

## Important limitation

This project is not production-ready for real payments solely because it builds or renders. Real payment acceptance, M-Pesa, inventory reconciliation, shipping rates, notifications, admin operations and launch compliance each require provider configuration, credentials and end-to-end verification.
